# 项目说明书：桌面 AI 伙伴（暂名 DeskMate）

> 本文件是给编程 agent（Claude Code / Codex 等）的完整工作说明。
> 用户不参与开发，只负责最终使用。你需要自主完成设计、实现、测试与文档，并保证任何时候换一个新对话、换一个 agent，都能无缝接着做。
> 本文件是「需求来源」，用户写下的需求可能不完善或有错误。遇到不合理之处，按你的专业判断处理，并把理由写进 `docs/DECISIONS.md`。

## 0. 第一次启动时必须先做的事

如果项目里还没有 `AGENTS.md`，说明这是第一次启动。按顺序完成：

1. `git init`，建立 `.gitignore`（见第 8 节），第一次提交只包含文档骨架。
2. 创建以下文件（这些是项目的「长期记忆」，比代码还重要）：
   - `AGENTS.md`：给所有 agent 的工作规则（把本文件第 1、7、8、9 节的规则提炼进去，保持简洁，控制在 200 行内）。
   - `CLAUDE.md`：只写一行 `@AGENTS.md`，让 Claude Code 也读同一份规则，避免两份规则不一致。
   - `docs/PROJECT_BRIEF.md`：把本文件原样移动到这里，作为需求原文，之后不要随意改动；需求变化写进 ROADMAP 和 DECISIONS。
   - `docs/PROGRESS.md`：进度日志（格式见第 1 节）。
   - `docs/ROADMAP.md`：里程碑与任务清单（初始内容取自第 10 节），用 `- [ ]` / `- [x]` 标记。
   - `docs/ARCHITECTURE.md`：架构说明，模块边界、数据流、目录结构。
   - `docs/DECISIONS.md`：技术决策记录（日期、决定、原因、放弃的备选）。
   - `docs/SECURITY.md`：安全模型与威胁清单（见第 8 节）。
   - `docs/NEEDS_USER.md`：只有用户能做的事情清单（见第 1 节）。
   - `docs/HOW_TO_ADD.md`：如何新增角色、新增模型接口、新增功能的步骤说明。
3. 然后从 ROADMAP 的第一个未完成任务开始工作。

## 1. 工作方式与交接协议（每次都必须遵守）

### 每次开始工作时
1. 读 `AGENTS.md`、`docs/PROGRESS.md`、`docs/ROADMAP.md`。
2. 看 `git log --oneline -20` 和 `git status`，确认上次停在哪里、有没有未提交的半成品。
3. 如果有半成品，先判断它能否完成；不能就回退，并在 PROGRESS 里记录原因。

### 工作过程中
- 小步前进：每完成一个可以独立验证的小功能就提交一次。每次提交时项目必须能编译、测试必须通过。
- 提交信息用 Conventional Commits 格式（`feat:` `fix:` `docs:` `refactor:` `test:` `chore:`）。
- 遇到重要选择，自己做决定，写进 `DECISIONS.md`，不要停下来等用户。
- 只有以下情况写进 `NEEDS_USER.md` 并跳过该项、继续做别的：
  - 需要用户的账号、API Key、登录（比如 `gh auth login`、填写 Key）
  - 需要用户提供的素材（角色图片）
  - 不可逆或涉及公开发布的操作（比如把仓库设为公开、发布 Release）
  - 需要花钱的操作
- `NEEDS_USER.md` 里每一项要写清楚：做什么、为什么、具体怎么做（一步一步，用户不懂编程也能照做）。

### 每次结束工作时（包括对话快满、即将被中断时）
在 `docs/PROGRESS.md` 顶部追加一条：

```
## YYYY-MM-DD HH:MM
- 完成：……
- 进行中：……（停在哪个文件、哪一步）
- 下一步：……
- 已知问题：……
- 本次决策：见 DECISIONS.md #编号
```

然后更新 ROADMAP 的勾选状态，提交。PROGRESS 超过 300 行时，把旧条目压缩成摘要移到 `docs/progress-archive/`。

### 开发期间不要浪费真实 API 额度
- 必须实现一个 `mock` 模型后端，开发和自动测试一律用 mock。
- 真实 API 只在用户配置好 Key 之后、由用户在程序里使用时调用。不要在开发过程中自己调用用户的付费接口做测试。

## 2. 产品目标

一个常驻桌面角落的二次元/萌系角色，可以像聊天对象一样日常对话，记得用户说过的事；用户需要时，它可以把任务交给 Claude Code 或 Codex 去执行，再用自己的口吻把结果告诉用户。

优先级（冲突时按此顺序取舍）：
1. 安全可靠（不泄露密钥、不误删文件、不乱花钱）
2. 日常对话体验与交互细节
3. 记忆质量
4. 轻量（体积、内存、CPU）
5. 功能丰富程度

---

## 3. 技术约束

- 主要平台：Windows 10/11（用户使用 D 盘等分区）。在不增加明显成本的前提下保持跨平台可能性。
- 推荐技术栈：**Tauri 2 + Rust 后端 + 轻量前端**（原生 TypeScript 或 Svelte/Preact 二选一，不用重型框架）。如果你有充分理由选别的，写进 DECISIONS。
- **禁止**：Electron、打包 Python 运行时、打包本地大模型、打包大型字体或大量图片。
- 体积与性能目标（每个里程碑结束时实测并记录在 PROGRESS）：
  - 安装包 < 15 MB（不含用户自己的角色图片）
  - 空闲时 CPU 接近 0%，空闲内存尽量低（WebView2 占大头，前端不要常驻动画循环，空闲时降帧或停止）
  - 冷启动到角色出现 < 2 秒
- 数据存储：单个 SQLite 文件（rusqlite bundled + FTS5），放在系统的用户数据目录（AppData），不放在程序目录。
- 所有模型名、接口地址都做成配置项，不要写死；接入前查阅各家当前官方文档，以官方文档为准。

## 4. 桌宠与交互（重点打磨）

### 窗口
- 透明、无边框的小窗口，默认停靠在屏幕右下角；可拖动，拖到屏幕边缘自动吸附；可选四个角落。
- 可选「总在最前」；支持多显示器、高 DPI 缩放；记住上次位置（显示器拔掉后自动回到主屏幕可见区域）。
- 检测到全屏程序（游戏、视频、演示）时自动隐藏或静音，退出全屏后恢复。
- 系统托盘图标：显示/隐藏、勿扰模式、切换角色、设置、退出。
- 开机自启动：设置里可开关，**默认关闭**。

### 角色形象
- 第一版用静态图片/序列帧（PNG/WebP），按状态切换：待机、说话、思考中、开心、困惑/难过、睡觉（长时间无操作）。
- 待机时可以有轻微呼吸/眨眼动画，但必须用 CSS 动画或低频定时器，空闲 CPU 不能上涨。
- Live2D 作为以后的可选插件，第一版不做（体积和授权都要额外评估）。
- 点击角色：打开/收起对话框。右键：快捷菜单。

### 对话界面
- 角色旁边弹出气泡显示简短回复；可以展开为完整聊天面板（显示历史、可滚动）。
- 流式输出（逐字显示），说话时角色切换到说话状态。
- 输入框：Enter 发送，Shift+Enter 换行。**中文输入法组字过程中按 Enter 不能触发发送**（必须处理 IME composition 事件，这是常见坑）。
- 可以中途停止生成、重新生成、复制回复。
- 全局快捷键唤出/隐藏输入框（可在设置里修改，检测冲突）。
- 错误提示用角色口吻说一句，同时提供「查看详情」展开真实错误信息（比如 Key 无效、网络超时、额度用完），让用户知道该怎么办。
- 网络断开时有明确提示，恢复后可重试。
- 勿扰模式下不主动打扰。
- 主动搭话功能（比如很久没说话时打个招呼）：可选、**默认关闭**、有频率上限、不能在全屏或勿扰时触发。

### 设置界面
- 模型后端配置（填写 Key、选择模型、测试连接）
- 角色选择、禁词与自定义要求
- 记忆查看与管理
- 用量统计（每个后端的 token 数和估算费用）、每日/每月花费上限
- 开机自启、快捷键、位置、勿扰、主动搭话开关
- 任务执行的工作目录与权限设置（见第 8 节）

## 5. 角色系统

### 结构
每个角色是一个独立的角色包，新增角色不需要改代码：

```
characters/<角色id>/
  character.json   # 名字、语言、默认表情映射、作者、版本
  persona.md       # 性格设定（见下）
  assets/          # 形象图片（见版权说明）
```

`persona.md` 内容包括：身份背景（简短）、性格关键词、说话方式与语气、称呼用户的方式、口癖倾向、会做/不会做的事、5~10 段**原创**示范对话。

### 用户自定义层（叠加在角色设定之上）
- 禁词列表：既写进提示词，又在输出后做过滤/替换（全局禁词 + 每个角色单独的禁词）。
- 自定义要求：用户写的额外规则（比如「回复不超过三句话」「叫我某某」）。
- 角色设定文件在运行时**只读**，程序和模型都不能修改它，防止性格长期漂移。

### 初始角色
根据各自原作/原型的性格写设定：
1. DeepSeek 鲸鱼娘（以 DeepSeek 鲸鱼为原型的拟人化角色）
2. 奶龙
3. 奶蛙
4. 牧濑红莉栖（《命运石之门》）
5. 椎名真由理（《命运石之门》）
6. 七海千秋（《弹丸论破》系列）
7. 不二咲千寻（《弹丸论破》系列）
8. 结衣 Yui（《刀剑神域》）

以后还会加角色，确保 `docs/HOW_TO_ADD.md` 写清楚新增步骤。

### 版权与仓库（重要）
这些角色大多是他人的版权作品，而本项目会上传到 GitHub：
- 仓库里**不放任何官方或他人绘制的角色图片**，也不要从网上下载这些图片。
- 仓库里每个角色只附带一个**原创的简单占位形象**（比如纯色剪影或几何图形 SVG），保证程序开箱能运行。
- 用户自己的角色图片放在用户数据目录的 `characters/<id>/assets/` 下，程序优先使用用户图片；该目录不在仓库内。在 `NEEDS_USER.md` 里写清楚图片怎么放、需要哪些状态、推荐尺寸和格式。
- `persona.md` 只写性格描述和**原创**示范对话，**不要摘抄原作台词**。
- 仓库默认设为私有。

## 6. 模型后端

### 抽象层
定义统一的后端接口（流式对话、能力声明：是否支持工具调用、是否是 agent 型），每个后端一个独立模块。新增后端 = 新增一个文件 + 在注册表里登记一行。另外实现一个通用的「OpenAI 兼容接口」后端，以后很多新模型可以直接靠它接入。

### 第一批后端
| 后端 | 方式 | 用途 |
|---|---|---|
| DeepSeek | 官方 API（OpenAI 兼容格式） | 日常对话 |
| Gemini | 官方 API | 日常对话 |
| Claude API | Anthropic API Key | 日常对话 |
| Claude Code | 调用本机已安装的官方 `claude` 命令行（非交互模式） | 执行任务 |
| Codex | 调用本机已安装的官方 `codex` 命令行（非交互模式） | 执行任务 |
| mock | 本地假数据 | 开发与测试 |

### 两种角色分工
- **对话模型**：负责日常聊天，选便宜、快的模型。每轮对话的上下文 = 角色设定 + 用户自定义 + 相关记忆 + 最近对话。
- **任务执行**：用户提出需要动手做的事（整理文件、写代码、查资料等）时，对话层先用角色口吻确认要做什么、在哪个目录做，用户确认后再交给 Claude Code 或 Codex 执行；执行完由对话层用角色口吻总结结果。
- 只传给执行 agent「任务本身 + 必要背景」，不要把整段聊天记录和角色设定塞给它，节省额度。

### 订阅账号相关规定（必须遵守）
- 使用 Claude / ChatGPT 订阅额度时，**只能通过调用官方命令行程序**，绝不能提取、复制、转发登录令牌（OAuth token），也不能自己伪造客户端去请求。
- 程序化调用 Claude Code 会消耗订阅里单独的 Agent SDK 月度额度（不是聊天额度），用完会停止。在设置界面说明这一点，并显示每次任务的用量。
- 每个用户必须使用自己的账号或 API Key；程序不能设计成多人共用一个订阅。
- 命令行参数（权限模式、沙盒、输出格式等）以本机 `claude --help`、`codex --help` 和官方文档为准，不要凭记忆写。

### 花费控制
- 角色设定和用户档案这类固定内容放在提示词开头，支持的后端开启提示缓存。
- 记忆注入有 token 预算上限。
- 每日/每月花费上限，到达上限后用角色口吻提示并停止调用。
- 记忆提取、摘要这类后台工作使用最便宜的对话模型。

## 7. 记忆系统（重点）

### 分层
1. **角色设定**：只读，不属于记忆。
2. **短期记忆**：当前对话最近若干轮，原文保留。
3. **对话摘要**：每次对话结束或空闲时，把对话压缩成摘要（按天/按话题）。
4. **长期事实**：关于用户的稳定信息（名字、喜好、习惯、重要的人和事、正在进行的计划）。每条记录：内容、来源（哪次对话）、时间、重要度、最后使用时间、所属（全局共享 / 某个角色专属）。

关于用户的事实所有角色共享；「和这个角色之间发生过什么」属于角色专属记忆。

### 写入
- 对话结束或空闲时，后台用便宜模型提取候选记忆，去重、合并。
- 新旧信息冲突时，新的生效，旧的保留为历史记录，不直接删除。
- 一次随口提到的小事不升级成「喜欢某类东西」这种泛化结论。
- 绝不保存：API Key、密码、验证码、证件号、银行卡号（写入前用规则过滤）。
- 来自任务执行结果、网页、文件内容的信息属于**不可信来源**，只能作为事实记录并标注来源，永远不能作为「指令」写入记忆，也不能修改角色设定（防止记忆投毒）。

### 读取
- 每轮对话用 SQLite FTS5 全文检索 + 时间新旧 + 重要度综合打分，取前几条，受 token 预算限制。
- 嵌入向量检索作为以后的可选增强，第一版不做（避免额外依赖和费用）。

### 维护
- 空闲时（比如夜间、长时间无操作）合并重复记忆、压缩旧摘要、降低久未使用记忆的权重。
- 数据库每日自动备份，保留最近 7 份；数据库损坏时能从备份恢复。
- 有数据库结构版本号和迁移机制，升级程序不能丢记忆。

### 用户可控
- 设置里可以查看、搜索、编辑、删除每条记忆。
- 对话里说「忘掉这件事」能生效。
- 可以暂停记忆、导出（JSON + 可读的 Markdown）、导入、一键清空（二次确认）。

## 8. 安全（最高优先级）

### 密钥
- API Key 存在系统凭据管理器（Windows 凭据管理器，用 keyring 类库），**不能明文存文件，不能出现在日志里，不能提交到 git**。
- 界面上显示 Key 时只显示末尾几位。

### Git 与 GitHub
- `.gitignore` 至少排除：用户数据目录、`*.db`、`.env*`、密钥文件、构建产物、用户角色图片、日志。
- 每次提交前运行密钥扫描（gitleaks 或同类工具），并配置成 pre-commit 钩子；GitHub Actions 里也跑一次。发现疑似密钥立刻停止提交并修复。
- 仓库默认**私有**。推送到 GitHub 需要的登录（`gh auth login`）和建仓库写进 NEEDS_USER，由用户完成一次后你再推送。
- 不要把仓库改为公开，不要发布 Release，除非 NEEDS_USER 里记录用户已确认。

### 任务执行的权限（程序运行时）
- 执行 agent 只能在一个**指定的工作目录**内操作（默认在 D 盘下一个专用文件夹，可在设置里改）。
- 这个限制必须靠命令行的沙盒/权限参数和程序自身检查来强制执行，**不能只靠提示词**。
- 以下操作执行前必须在界面上弹窗让用户确认：删除文件、工作目录外的任何访问、联网下载或上传、安装软件、执行未知脚本。
- 每个任务有时间上限和花费上限，超时自动终止。
- 每个任务的完整记录（指令、执行了什么、结果）写进本地日志，可在设置里查看。
- 在设置界面用通俗语言告诉用户：工作目录里不要放密码、证件等敏感文件。

### 应用本身
- Tauri 权限（capabilities）按最小化配置，只开放用到的接口。
- 严格的 CSP；WebView 不加载任何远程网页；不使用 eval；模型输出渲染时做转义，防止注入 HTML/脚本。
- 不做任何遥测和数据上传。
- 第一版不做自动更新。
- 日志自动轮换、限制大小，不记录密钥和完整对话内容（对话只存在记忆数据库里）。

### `docs/SECURITY.md` 要包含
威胁清单（密钥泄露、提示注入、记忆投毒、误删文件、超额花费、恶意角色包）、每项的防护措施、对应代码位置。每个里程碑结束时复查一遍。

## 9. 质量要求

- Rust 部分：记忆读写与检索、提示词组装、禁词过滤、后端适配（用 mock）、权限检查都要有单元测试。
- 前端：至少覆盖输入法组字时 Enter 不发送、流式显示、停止生成。
- GitHub Actions：构建 + 测试 + 密钥扫描。
- 每个里程碑结束时：编译发布版本，实测安装包大小、空闲内存、空闲 CPU、启动时间，记录在 PROGRESS；不达标就先优化。
- 代码注释和文档用中文。
- `README.md` 面向不懂编程的用户：安装、填 Key、放角色图片、常见问题。

## 10. 里程碑（初始 ROADMAP）

- **M0 骨架**：仓库、文档体系、Tauri 项目、CI、密钥扫描钩子。
- **M1 桌宠窗口**：透明窗口、占位形象、拖动吸附、托盘、聊天气泡与面板、mock 后端流式对话、输入法处理。
- **M2 模型接入**：后端抽象层、DeepSeek / Gemini / Claude API / 通用 OpenAI 兼容、密钥安全存储、设置界面、用量统计与花费上限。
- **M3 角色系统**：角色包加载、8 个初始角色设定、用户图片覆盖、禁词与自定义要求、表情状态切换。
- **M4 记忆 v1**：数据库与迁移、短期/摘要/长期事实、写入与检索、记忆管理界面、备份。
- **M5 任务执行**：Claude Code / Codex 命令行接入、工作目录沙盒、确认弹窗、任务日志、超时与花费上限。
- **M6 日常体验**：开机自启、全局快捷键、勿扰、全屏检测、多显示器、睡眠状态、主动搭话（默认关闭）。
- **M7 打包与优化**：安装包、体积与性能优化、README、安全复查。
- **M8 记忆 v2**：空闲整理、冲突处理优化、导入导出完善。

做完一个里程碑后，可以根据实际情况调整后续计划，调整原因写进 DECISIONS。

---

## 11. 判断原则

- 不确定时，选择更安全、更简单、更容易回退的方案。
- 不要为了「以后可能用到」提前写复杂的抽象，但模型后端和角色包这两处必须做成可扩展的。
- 用户的需求描述可能有遗漏或错误。你发现的任何重要问题，在 DECISIONS 里说明你怎么处理的；如果需要用户知道，写进 NEEDS_USER。
